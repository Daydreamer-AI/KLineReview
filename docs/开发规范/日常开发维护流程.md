# 日常开发维护流程

> 本文档定义 KLineReview 的日常需求、开发、自测、合并、发布与维护流程，供开发者与 Agent 共同遵守。标注“（已确认）”的内容来自仓库当前实际状态（2026-08-19）；其余为建议规则，未确认事项统一标注 `TODO`。

## 1. 目的与原则

- 目的：让每个变更都可追溯（需求 → 分支 → 提交 → 文档），降低沟通成本，使 Agent 无需每次对话重复确认规则。
- 原则：
  1. **先文档、后开发**：新增需求/功能必须先有需求文档；
  2. **一切变更走分支**：不在主干上直接提交（建议，远端当前无保护规则可确认）；
  3. **提交可读**：提交信息遵循统一格式；
  4. **变更同步文档**：影响目录结构、入口、命令或规范时，同步更新相关文档。

## 3. 需求与功能文档规则

**结论：新增需求、功能、模块时，必须先在 `docs/需求文档/<版本>/<模块>/` 下创建需求文档；缺陷修复不强制，但涉及数据库 schema、对外接口或用户可见行为时必须补充说明。**

1. **新增需求/功能/模块**：动手开发前必须创建 `docs/需求文档/<版本>/<模块>/<YYYYMMDD>-<功能名>.md`，复制 [需求文档模板](../需求文档/需求文档模板.md) 填写；模块归类规则见 [模块划分说明](../需求文档/模块划分说明.md)（按主要影响模块归类，无法判定时放 `跨模块/`）。
2. **缺陷修复（bugfix）**：不强制创建需求文档，在提交信息中说明即可；若涉及数据库 schema、对外接口或用户可见行为，需在对应需求文档中追加“变更说明”，或在 `docs/需求文档/` 下补充说明文档。
3. **文档更新时机**：
   - 开发前：创建文档，状态为“草稿”；
   - 开发中：记录分支、关键决策；
   - 完成后：状态改为“已完成”，记录提交、自测结果与验收情况。

## 4. 日常开发流程

### 4.1 需求阶段

1. 确认需求，创建需求文档（复制模板到 `docs/需求文档/<版本>/<模块>/` 并重命名）；
2. 填写背景/目标、功能点、验收标准、影响范围；
3. `TODO`：需求编号（如 `REQ-001`）与评审机制待团队确认，当前单人开发可自行检查。

### 4.2 开发阶段

1. 阅读必读文档：[AGENTS.md](../../AGENTS.md)、[docs/项目导读.md](../项目导读.md)、[版本控制.md](版本控制.md)、本文件；
2. 按 [版本控制.md](版本控制.md) 的命名规范创建分支（如 `feature/<模块>-<简述>`，从 `release/1.0` 切出）；
3. 开发并自测：从项目根目录运行 `python ./src/main.py` 冒烟验证，检查 `data/logs/` 是否有新报错（当前无自动化测试，已确认）；
4. 提交：使用 Conventional Commits（`feat`/`fix`/`docs`/`refactor`/`test`/`chore`），并遵守 [AGENTS.md](../../AGENTS.md) 的提交前检查；
5. 更新需求文档状态与开发记录。

### 4.3 合并与发布阶段

1. 合并回 `release/1.0`（多人协作建议 PR/MR 评审，`TODO` 待确认）；
2. 合并后再次冒烟验证；
3. 版本稳定后由 `release/1.0` 合并到 `master` 并打 tag `vX.Y.Z`（规则见 [版本控制.md](版本控制.md)）；
4. 发布后更新受影响文档（项目导读、AGENTS.md）。

## 5. Agent 自动执行规则

以下规则已写入 [AGENTS.md](../../AGENTS.md)，Agent 接到任务时自动遵守：

1. **新需求/功能必须有需求文档**：若 `docs/需求文档/` 下无对应文档，先按模板创建再开发；
2. **开发前必读**：AGENTS.md、项目导读、版本控制.md、本文件；
3. **分支与提交**：遵循版本控制.md 的分支命名与提交规范；
4. **自测**：无自动化测试，须冒烟验证并检查日志；
5. **文档同步**：完成后更新需求文档状态；改动影响目录/入口/命令时同步更新项目导读与 AGENTS.md；
6. **不确定事项标注 TODO**，不猜测。

## 6. 日常维护清单（建议周期性执行）

- 交易日数据更新：按 [README.md](../../README.md) 与 `scripts/` 规则执行数据脚本（与主程序互斥，已确认）；
- 定期清理 TODO：处理 AGENTS.md 与文档中的待确认项；
- 依赖审查：`requirements.txt` 未锁版本（已确认），发布前应锁定或验证依赖版本。
