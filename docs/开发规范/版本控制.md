## 3. 分支模型与命名规范

### 3.1 当前分支（已确认）

- `master`：长期主干分支，对应可发布/稳定的代码基线。
- `release/1.0`：1.0 版本的开发/发布分支，已合入 `master`；README/文档收尾仍在本分支提交。

### 3.2 建议的分支命名规范

以下为建议，需团队确认后写入规范（`TODO`）：

| 分支类型 | 命名格式 | 示例 | 说明 |
| --- | --- | --- | --- |
| 版本开发/发布线 | `release/<版本号>` | `release/1.0` | 版本级开发与发布准备 |
| 功能分支 | `feature/<模块>-<简述>` | `feature/kline-animation-refactor` | 单个功能的开发 |
| 缺陷修复 | `fix/<模块>-<简述>` 或 `bugfix/<编号>-<简述>` | `fix/review-trading-calc` | 缺陷修复 |
| 紧急修复 | `hotfix/<简述>` | `hotfix/login-failure` | 线上紧急修复 |

### 3.3 分支生命周期（建议）

1. 从 `master` 或 `release/1.0` 切出功能/修复分支；
2. 在分支上开发并提交；
3. 完成并自测后合并回来源分支（推荐 Pull Request / Merge Request 评审后合并）；
4. 版本稳定后由 `release/1.0` 合并到 `master`，并打版本 tag。

## 4. 提交信息规范

### 4.1 现状（已确认）

- 近期提交已使用 Conventional Commits；历史提交仍有中文描述式。无提交模板、无 lint 校验；CI 目前只运行 unittest。

### 4.2 建议规范

建议采用 Conventional Commits 风格，`type(scope): description`，description 可用中文：

```text
feat(kline): 新增分钟线回放动画
fix(review): 修复模拟交易收益率计算错误
docs: 更新版本控制说明
refactor(db): 重构股票数据库连接池
test(indicators): 补充 MACD 计算单测
chore: 升级依赖版本
```

常用 `type`：`feat`（新功能）、`fix`（修复）、`docs`（文档）、`refactor`（重构）、`test`（测试）、`chore`（杂项）。

## 5. 版本号与标签

- 当前仓库无任何 tag（已确认），尚无版本号约定。
- 建议采用语义化版本（SemVer）`vX.Y.Z`：
  - `X` 主版本：不兼容的变更；
  - `Y` 次版本：向后兼容的新功能；
  - `Z` 修订号：向后兼容的缺陷修复。
- 建议在 `master` 上每次达到可发布状态时打 tag，如 `v1.0.0`。

## 6. 合并与发布流程（建议）

```text
feature/* ──┐
fix/*    ──┼──> release/1.0 ──> master ──> tag v1.0.0
hotfix/* ──┘        │              │
                    └── 版本自测 ───┘
```

要点：

1. 日常开发在 `release/1.0` 或功能分支上进行，避免直接在 `master` 上提交（建议，当前无远端保护规则可确认）。
2. 合并前运行 `python -m unittest discover -s tests -v`，并按 [AGENTS.md](../../AGENTS.md) 冒烟验证。
3. 发布时从 `release/1.0` 合并到 `master` 并打 tag，发布说明（Release Notes）记录主要变更。
